# R02q — legacy byte-table transaction

R02q replaces the legacy `EXE_PATCHES` loop of independent writes with a bounded validate, write, verify and rollback transaction for the **same 21 descriptors** (18 enabled by current compiled defaults). The existing R02p read-only preflight still checks effective-enabled rows before the first `Install()` native patch. At the original byte-table installation point, the new bridge resolves the same RVAs and byte arrays, checks each enabled span belongs to readable EXE image memory, and calls the focused `LegacyByteTransaction` module through the existing Win32 `MemoryAccess` backend. Effective-disabled rows are counted as skipped without imposing a signature dependency. A failed table transaction now aborts later legacy installers and reports its outcome; previously installed sibling hooks are not rolled back by this table-only transaction.

The transaction rejects malformed, out-of-range, duplicate or overlapping enabled rows before protection changes. It verifies every enabled expected byte before writing, prepares journals and reporting storage, acquires all protection tokens, then writes and reads back each replacement in table order and flushes instruction cache. A failed or partial write, readback, flush, or protection restoration triggers reverse recovery of every touched row, including the row whose write failed, followed by reverse restoration of remaining tokens and a final byte check. `RolledBack` means recovery checks passed; `RollbackFailed` identifies incomplete byte or protection recovery. These results are not a claim of process-wide atomicity or repair of earlier installers. The existing hard startup decision remains **WITHHELD**, so production currently installs zero sites and no candidate was launched or deployed.
