# R02w — authenticated static D3D device-template transaction

R02w installs Reset and Present hooks in the pinned provider's two static image templates **before** forwarding `CreateDevice`. Native code on the bounded A/B constructor path copies 175 DWORDs from one template into a device-owned embedded table, and a Reset path can copy 119 DWORDs from the saved template again. The new transaction journals only four provider-image DWORDs: A/B slots 16 and 17. It never writes or retains a returned COM object's writable heap vtable. Production startup remains Rejected/WITHHELD; this work does not authorize a candidate or certify the original game's D3D phase.

## Implementation and finite contract

The adapter reuses R02t's pinned provider file and mapped-text authentication, retained module reference, exact EXE import and factory-table prerequisites, no-wait gate, provider-image storage checks, aligned compare-exchange, reverse recovery and terminal poison on incomplete recovery. It resolves the four current A/B slot values from the authenticated disk snapshot plus actual relocation base. All four must match pinned native Reset/Present entries, both A/B method tuples must agree, and the static spans must be committed immutable provider image storage. Both original method pointers are published before any hook CAS. A possible historical exposure retains those originals and the provider reference even after clean rollback. A repeated call verifies the owned import, factory and template slots without changing them; a foreign edit or changed storage fails closed.

`HookCreateDevice` preserves its existing FPU-preserve flag, `ForceImmediatePresent` processing, provider arguments, HRESULT and returned object. It invokes the template transaction before the original provider call. On success, a bounded read-only check during the same callback verifies the returned device points to its embedded table at object+`0x2F5C`, saved template at object+`0x2F58` is A/B, and copied slots16/17 contain the two hooks. The check stores no COM or heap-table pointer. Failure reports D3D unavailable while returning the provider's result to the game. The historical image-backed table API remains for owned tests but has no production caller. Template C, foreign provider/table, already-created objects and unproved derived-device paths are unsupported; no heap guard is relaxed.

The four slot CAS operations are individually atomic, not one process-wide atomic publication. Supported use still requires a verified exclusive native installation phase. Earlier D3D import/factory effects can remain if a later stage fails; this is a bounded template-group transaction, not a whole-DLL rollback. Frozen MP/FPU/POP/savings behavior, effective settings, and gameplay balance are unchanged. `HookPresent`'s transitive UI/diagnostic/frame-cap callbacks and M3 other-thread phase remain separate open conditions.

## Verification and limits

Luna's actual-source owned x86 fixture passed **23 cases and 655 checks** with zero failures. It covers both templates at a relocated surrogate base, preparation before writes, four-stage CAS and reverse protection restoration, failed/mismatch CAS, readback and protection faults, terminal poison, reentrancy, foreign edits, and read-only returned-copy acceptance/rejection. Both historical D3D test entrypoints passed **25 cases and 555 checks** each with zero failures after the narrow test-only caller update. The exact private source hashes, commands and outputs are retained outside Git. These fixtures do not run proprietary game code or certify the original game's provider phase.

The clean isolated Release Win32 build passed in the private `R02w/build-final` tree with no game deployment. Its source, exports, PDB and compiled installer-order audit remain under independent review.

The owned real-system SDK route first showed a concrete Windows mediation boundary. The initial dynamic lookup and a separate ordinary static-import diagnostic both resolved the SDK entry through x86 `apphelp.dll`, so neither was used to claim direct pinned-provider behavior. A numbered, root-reviewed ordinary static-import diagnostic authenticated both system files and its exact EXE IAT target `apphelp+0x812F0`, then called the documented `Direct3DCreate9`. Its returned factory's vptr was in pinned d3d9 RX image storage, but `CreateDevice` slot16 pointed to authenticated apphelp code at `apphelp+0x80E10`, rather than pinned native d3d9 `+0x40050`. It stopped at that explicit method precondition, released the factory to zero and cleaned up without creating a device, reading private device fields or writing provider memory.

One further numbered owned-process variant added only an embedded Windows supported-OS manifest, retaining the strict **direct** named-import and native factory-method checks. On this host its EXE IAT and `GetProcAddress` both resolved to pinned d3d9 base+`0x815D0`; the factory vtable's `CreateDevice` slot16 resolved to pinned d3d9 base+`0x40050`. Through that documented x86 SDK route, a hidden owned window and flags `0x42` produced `CreateDevice` `S_OK`, a device vptr equal to device+`0x2F5C`, saved template A at provider+`0x1008`, and Reset/Present slots matching both A/B static templates. `Reset` returned `S_OK` and preserved that structure. Release returned zero; a second creation returned `S_OK` with the same bounded structure, followed by zero-reference Release, factory Release and complete cleanup. This **supports native layout/copy behavior on the owned manifested process**, not hook inheritance after provider-image modification, the original game's whole D3D lifecycle/phase, or any apphelp-mediated consumer profile. No real provider bytes were modified in these SDK runs.

S02/R02 therefore remain incomplete, S03 stays closed, and no performance measurement is claimed. The original game's D3D provider/lifetime/phase and the current hard startup gate remain authoritative for any later controlled candidate decision.
