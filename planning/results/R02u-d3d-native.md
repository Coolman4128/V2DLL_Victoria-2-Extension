# R02u — original-Lua/HPM D3D native interface disposition

R02u captured the ordinary original-Lua/HPM D3D factory and device-creation route without installing the fork DLL or changing the game. The finite result is **blocked for the current R02t D3D installer profile**: the returned device object's vtable resides in writable `MEM_PRIVATE` memory, while that installer deliberately accepts only an authenticated image-backed table. This is an observed unsupported condition, not evidence that D3D cannot be supported by a future, separately proved adapter. The production startup gate remains Rejected/WITHHELD, S02/R02 incomplete and S03 closed.

No candidate hook was installed.

## Capture bounds, preservation and disposition

The first original-Lua run armed two EXE factory callsite hardware breakpoints after an imm32 loader stop; neither fired before the visible menu. Its 90.5100249-second active interval is historical no-hit evidence only: startup may already have passed those calls. A benign owned x86 suspended-start surrogate then showed one host `ResumeThread` returned debugger-adjusted prior count `2`; after one GDB continue and a pinned ntdll attach trap, a hardware breakpoint stopped at the expected surrogate target before its marker. This established a bounded earlier-arm procedure without engine code. The second original-Lua run used that procedure and produced the factory and CreateDevice pairs above. One initial trial expecting suspend count `1` was stopped and closed without target hit; it was not treated as proof.

The D3D hardware-breakpoint family ledger counted both original-game attempts and all stopped inspection/setup time from each `before-install` through confirmed deletion. Cumulative active time was **317.6813228 seconds** (90.5100249 + 227.1712979), below the 480-second read-stop and 600-second hard limit. A retained-handle watchdog bound to the exact game/GDB process identities observed `WATCHDOG-NORMAL-DISARM`; no emergency termination or frame-by-frame Present breakpoint occurred. An initial unprefixed hex argument to the private mapped-text dumper failed before any read, was recorded as such, and the correctly prefixed capture succeeded. A separate early query of an unrelated export address was likewise discarded and corrected before use.

The game was closed through its owned main-menu Exit control; GDB recorded normal inferior exit and logging-off, and both owned PIDs were absent. Against a fresh 929-file/609,015,240-byte attempt02 backup, exactly four HPM log files changed. Their generated versions were archived privately, then only those four verified backups were restored. The final manager comparison and independent root rehash found **929 same, zero changed/missing/added**. Attempt01 received the same exact restoration. Neither run changed a save, installed executable/DLL, configuration, display setting or the user's separate game.

The supported facts close the finite R02u observation objective and identify a concrete blocker for the present D3D adapter: native device vtable storage is writable private memory. The next coherent D3D work, if assigned, must establish whether that dynamic table has a safe device-scoped ownership/Release/reset lifecycle and exclusive publication phase, then adapt or explicitly reject that actual route. It must preserve provider HRESULT/object behavior and the current hard startup gate until every active dependency is supported. Frozen MP/FPU/POP/savings behavior and settings remain untouched; no performance result is claimed.
