## Direct lookup and glue dispatch contracts

The native Technology creation routine provides an exact counterpart to `SetupButtons`: it constructs stack string objects for `start` and `selected_tech_window`, reads container `[view+0x4C]`, invokes container vtable `+0x6C` at call `0x3AC068` with one string-object pointer, invokes returned host vtable `+0x34` at `0x3AC076` with the other string-object pointer, then invokes the returned button's observable at `button+0x54`, vtable `+4`, call `0x3AC084`, passing the native glue at `view+0x60`. These three calls are exact reached instruction boundaries in the 927-instruction creation CFG. The native strings are released immediately afterward, so the source's transient-key call shape has a direct native analogue. This does not alone establish retention behavior of every possible dynamic lookup subtype.

The manager's second-campaign Technology container had vptr RVA `0xA3C0D8`. Its disk slots `+0x6C` and `+0x34` independently have HIGHLOW relocations to the following bodies:

Searches object `+0x424` via helpers `0x5E68A0` and `0x5E6960`. Missing-window branch formats and emits a native warning before returning zero; it is not a pure/no-side-effect lookup. |

All these body CFGs have no unresolved direct jumps or decoding stops; indirect **calls** remain dependencies even though traversal proceeds past them. No complete thread/phase or exception-path claim follows from those counts. The observed container's own `+0x34` slot does not prove that a returned host has the same vtable/subtype.

The directly called search helper `0x5E6B30` has a 92-instruction CFG. It receives the key in EAX, allocates a temporary stack copy, copies the characters, lowercases the copy through imported `USER32!CharLowerBuffA` at IAT RVA `0x88A2C8`, compares against entries, and returns a found object pointer or zero. It restores its stack and nonvolatile registers on both normal returns, and does not store the original key pointer into a persistent field in this body. Its two collection-pointer arguments use caller cleanup, as confirmed by `add esp,8` after each call in `0x5E4C80`. The existence helper `0x5E68A0` has 65 instructions and `ret 8`; it reads size/capacity at string `+0x10/+0x14` and compares without a persistent key-pointer store. The access helper `0x5E6960` has 98 instructions and can copy/insert a key on its own missing-key branch. The outer `+0x6C` body invokes it on the found branch after the existence check; concurrent invalidation between those calls has not been excluded. Native caller string lifetime supports the synchronous key use, while full lifetime/phase closure remains open.

For all three proved glue tables, vtable slot 2 (`+8`) has HIGHLOW relocation to `0x337D00`: read callback `[glue+8]`, test for null; if nonzero, load owner `[glue+4]` into ECX and tail-jump to the callback; otherwise plain `ret`. This establishes the direct patched-click-method shape: owner in ECX, no supplied stack arguments, ordinary return. It independently supports `OFF_GLUE_METHOD=8` and owner offset 4; it does not prove that arbitrary additional method fields in a 44-byte clone can be retained safely.

Each glue table's slot 0 points to `0x20D0C0`, a scalar-deleting-destructor-shaped function: reset the vptr, test flag bit 1, optionally invoke deletion on the glue pointer, return with `ret 4`. Thus the registration/removal contract must establish whether the observable ever deletes the observer and how callbacks stop before view teardown. A static storage clone cannot be certified merely because its click callback ABI matches. The manager's asset audit reports the legacy custom buttons absent in pinned vanilla/GHM assets; that is conditional reachability evidence, not a proof of native observer ownership or every missing-child fallback.

The container constructor at `0x5E16C0` independently writes the primary vptr `0xA3C0D8` at `0x5E171E`, writes embedded vptr `0xA41E84` at `object+0x370` in instruction `0x5E19B6`, and clears `object+0x374`. All are reached in its 1,859-instruction CFG, with no unresolved jumps or decode stops. Embedded table `0xA41E84` has HIGHLOW slots `+4` to `0x241BA0` and `+8` to `0x5E6B10`. Including that direct tail target gives 51 reached instructions, no unresolved jumps or decode stops. Its visible body reads the supplied key without retaining the key pointer, and calls a character normalization helper. This bounds the fallback for the **constructor's** known subtype; it does not prove a returned host's live subtype or whether its tree remains empty after construction.

Source `MakeStr` writes short keys inline with capacity 15; longer keys borrow shared `g_nameStorage`. The name getter's output has a different ownership rule: for the observed descriptor, it returns a GStr object **inside the descriptor**, and `GStrText` borrows either that inline character array or its owned heap pointer. `OnTooltip` uses the borrowed characters immediately for `strcmp` and does not retain them across a tick. Nevertheless the wrapper calls this getter **after** the original tooltip method returns, so element and descriptor validity through that post-call access must be established. Immediate use is not a replacement for lifetime proof. The static source cache of view pointers and the hide-colonial retained owner remain separate open lifetime cases.

## Remaining closure and fail-closed consequence

1. **Complete callers and safe phase:** specific caller boundaries above are corroborated; a complete caller set, thread identity, safe mutation phase, reentrancy and exception paths remain uncertified. The probe's linear executable sweep is incomplete candidate discovery, not an exhaustive caller map. It does not cover `mov reg,[vtable+slot]; call reg` reliably. Source helpers need a contract for the observed construction and tooltip phases, rather than treating either as a simulation command phase.
2. **Lifetime:** primary-vptr construction/teardown writes prove that these objects have lifecycle transitions, not a validity guarantee. Callback registration/removal and teardown exclusion must be traced. Source cached addresses need generation/lifecycle evidence: address equality alone cannot distinguish a newly allocated view at a reused address. No native pointer retention is newly authorized.
3. **Custom callback dependencies:** `OnViewUpdate`, `SetupButtons`, hide-colonial setup, tooltip result/element interpretation and their native helpers/globals need the disjoint source-lane dependency audit. The native slot/RTTI facts do not validate offsets, callback glue, custom controls or metadata ownership.
4. **Installation:** a narrow prepared dependency record can require the exact disk fingerprint, PE mapping, expected relocated original slot target and class identity. RTTI + decoded vptr writers + native stack/return facts justify these slot targets, rather than copying whatever target happened to be present into an expected signature. They do not justify enabling the family while any runtime/callback dependency remains unproved. Validate all four slots before any write, reject changed slots, and roll back a partial installation; production remains inert behind the complete active gate.

No executable, game configuration, DLL, settings, shared source or live process was modified by this lane. The native/runtime exit for this family remains **NOT MET**. Required next evidence is a bounded caller/lifecycle/phase investigation of these exact four callbacks, with controlled game evidence only after the complete active startup gate permits it. Nothing here completes parent S02 or supports launching a partially verified DLL.
