## Target and scope

- Primary goal: speed 5 simulation completes a calendar year in **less than 12.0 seconds** on the user's hardware, with **Greater History Mod (GHM) 0.6 as the primary performance workload**. Backup goal: **less than 30.0 seconds**. Report these separately; reaching the backup does not mean the primary succeeded. Vanilla remains the original-behavior reference and an additional performance matrix.
- Hardware inventory supplied by the coordinating agent: Ryzen 7 9700X, 8 cores/16 logical processors, RTX 5070 Ti, approximately 93.3 GiB OS-visible RAM. Capture the actual machine, RAM configuration, Windows build, storage, display resolution, GPU driver, power plan, clocks and thermal conditions with the benchmark manifest. Do not infer performance from the specifications.
- Freeze existing multiplayer stabilization as **DONE — awaiting user testing**. Do not optimize its arithmetic, rewrite its synchronization, add MP diagnostics, or investigate old OOS cases. Regression checks for newly introduced behavior are quality gates, not a reopened MP improvement project.
- Preserve all actual simulation work and established bug fixes. No speed gains through fewer countries/POPs, less frequent AI/economy/event updates, altered RNG consumption, skipped ticks, changed economic precision, or reduced simulation fidelity. New requested military features are intentional exceptions to original gameplay; performance optimizations are not.
- Claim the target for each tested fixture and configuration only. No claim of universal sub-12-second years across arbitrary mods, dates, or wars is justified.

Dates describe desired fixtures, not saves claimed to exist. If unavailable, generate them in an isolated campaign and record provenance in a separately bounded fixture session. Do not fabricate a late-game benchmark by moving the date forward or adding fake POPs.
3. The user confirmed **Greater History Mod (GHM) 0.6**, not Greater Flavor Mod (GFM); installation is complete as recorded in [environment.md](environment.md). Use its exact installed release/data hashes for the primary early/mid/late matrix. The vanilla matrix is the behavior reference and secondary performance report. Missing GHM fixtures leave the primary goal unverified; vanilla-only timing cannot satisfy it. The military automation is for human players only; feature-load fixtures must reflect this.
4. Fix the same player country and no-input scenario for each comparison. Prevent incidental popup pauses using supported message settings; preserve event evaluation/effects. If an unavoidable choice appears, record a fixed scripted/native input sequence and replay it at the same game dates. Reject runs with unexplained pauses or diverging input history.
5. Fresh game process and the same starting save per replicate. Warm up one **calendar month**, then measure the following **12 calendar months** at speed 5. Starting boundary/date and RNG/state snapshot after warmup must match in A/B correctness runs. Add a separate continuous five-year run after acceptance to detect accumulating leaks/stalls. Warmup is not an excuse to omit expensive recurring month/year boundaries.
6. Start with three screening runs per fixture/candidate. Final acceptance uses five valid fresh-process runs per required fixture/configuration, interleaving baseline/candidate to reduce temperature/background-load bias. Record all runs; reject only documented external interruptions. Report median, minimum, maximum, and raw values. If noise masks a proposed improvement, obtain more evidence in a new bounded session rather than selecting the fastest run.

### Timing definition

- Authoritative metric: wall-clock elapsed QPC time between matching completed daily simulation boundaries for an exact calendar-year interval at speed 5. Include ordinary rendering, AI queue waits, audio, scheduling and continuous foreground game operation. Exclude initial program/save loading and the explicitly logged warmup only.
- Instrument a verified daily **completion** boundary; the existing `AccChkEnter` is an entry, not automatically the correct completion boundary. If consecutive entries are initially used as an interval proxy, prove that a full daily cycle lies between them and label that method. Check the game date advances exactly as expected, and distinguish entry timestamps from time spent inside the daily routine.
- Prefer one fixed-size timestamp record per day buffered in memory and flushed after the sample. Validate observer overhead by comparing a minimal-timing build/configuration to a control run. Microsoft documents [QPC for elapsed intervals](https://learn.microsoft.com/en-us/windows/win32/api/profileapi/nf-profileapi-queryperformancecounter).
- Record actual elapsed game days and years. `seconds_per_year = elapsed_seconds / measured_calendar_years`; `days_per_second = completed_days / elapsed_seconds`. At 365 days, 12 seconds means about **30.42 days/s / 32.88 ms/day**; 30 seconds means about **12.17 days/s / 82.19 ms/day**. Preserve real calendar behavior and record leap years if the engine uses them.
- Report daily median/p95/p99/max duration and total wall time separately. Do not sum overlapping per-thread CPU timers to produce wall time. FPS, loading time and UI response are secondary metrics, never substitutes for seconds/year.
- Primary test is foreground, normal rendered gameplay at fixed settings. A second diagnostic low-render-cost view may isolate a bottleneck, but minimized/headless/blank-map results cannot satisfy the gameplay target. Keep audio and normal map rendering available. Compare frame caps/VSync as explicit supported configuration variants, not invisible test-only changes.
- No autosave during raw throughput sample; disclose this. Run a separate normal autosave scenario, report each save stall and inclusive year time. Do not advertise the no-autosave measurement as an inclusive result.
- Performance configuration can disable observational RNG/state probes using existing switches while retaining crash/error reporting and the approved frozen MP logic. Keep baseline and candidate diagnostic settings identical. Correctness runs enable existing probes and are reported separately, never compared against clean timing runs.

### Acceptance and gates

- **Primary achieved:** every required GHM early/mid/late fixture has median year time <12.0 s, with raw distribution disclosed. **Backup achieved:** every required GHM fixture has median <30.0 s. Report the same thresholds for the vanilla matrix separately. A fixture that misses is explicitly a miss; an excellent early year cannot conceal a poor late year. Distinguish vanilla semantics from changes authored by GHM itself: the fork removes its own unrelated gameplay changes, not the user's chosen mod content.
- Mark runs with >5% coefficient of variation as unstable and investigate the source before using them as release evidence. This is a planning noise threshold, not a physical guarantee.
- A change is accepted only if correctness checks pass and its measured gain exceeds observed noise, with no material regression in another fixture. Predeclare the material regression threshold as >5% median slowdown, then consider tighter limits once measurement noise is known. Small reproducible wins can still accumulate.
- In feature-off equivalence runs, compare baseline/candidate initial and daily state, RNG order/counter, event outcomes, dates, and targeted AI/CB decisions. Identical probe hashes are necessary where expected, insufficient alone. Native same-build repetitions first establish which fields are stable; do not normalize away unexplained differences.
- New features enabled: validate their intentional military changes against their own contracts, and monitor economy/AI/event systems for unintended changes. Disabled features must have negligible runtime overhead.
- Cap UI blocking: measure selection/move response and event-loop stalls during the same run. The upstream 250 ms AI queue budget is a hypothesis to review, not a suitable unmeasured responsiveness promise. Track maximum queue age and work completed so throughput cannot be improved by starving queued work.

## Optimization order and stopping decisions

1. **Measure overhead before changing native logic.** Benchmark existing diagnostic switches. If profiles justify it, add a single diagnostic-timer setting and gate only observational timer work. Preserve shared daily normalization, existing army-window fix, D3D FPU preservation, crash support, and required feature dispatch. Do not refactor the entire monolith merely to benchmark.
2. **Profile CPU and waits independently.** Use WPR/WPA sampled CPU stacks plus precise scheduling/wait analysis, recording DLL PDBs and original executable RVA addresses. The Windows guidance distinguishes [sampled CPU activity and scheduling analysis](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis). Short traces avoid collecting a huge all-purpose recording. If profiler tooling is unavailable, record that dependency and use verified coarse phase timers as the bounded fallback.
3. **Audit existing optimizations for fidelity.** Shadow-test parallel predicates and inspect trigger purity; exercise same-day flags, decisions changing another country's eligibility, event effects altering later triggers, ownership changes, and save reload. Retain uncertain optimizations disabled in the release fidelity profile until validated. This concerns original gameplay correctness, not new multiplayer repair. Never simply turn on more workers to hit the time target.
4. **Tune low-risk overhead measured hot.** Prefetch on/off and placement; redundant buffer allocations; per-day rebuilt metadata; exact-result reuse inside a proven immutable scope; UI invalidation or rendering work shown to be redundant. Each change must retain call order, data lifetime, arithmetic and invalidation. Cache only with a documented dependency/invalidation model; do not cache arbitrary mutable predicates all day.
5. **Address the dominant native phase only after evidence.** If economy/POPs, route finding, AI scans or trigger evaluation dominates, choose one function, recover its input/output and side effects, and build a native-vs-replacement comparison path. Replacements retain fixed-point overflow/rounding, update order, RNG calls and native fallback. Do not precommit to SIMD/parallel economy without proving compatibility. Rewrite only enough to produce a measured win.
6. **Tune worker utilization only if relevant.** Current custom pool and TBB can overlap/oversubscribe. First measure wakeups, worker active time, serial fraction, and actual TBB thread count. Changing pool size or task granularity is contingent on trigger purity/equivalence. Never alter frozen FPU or quantization settings as a performance experiment.
7. **Budget new features.** Template and transport controllers use bounded job queues and game-date/event-driven updates; idle controllers do no world scans. Measure idle, 10, and 100 simultaneous jobs (fixture permitting), growing queue memory, and capped work per tick. No wall-clock-dependent simulation decisions. Use native path/recruitment queries, stable IDs, and caches with invalidation where verified.

For baseline year time `T` and measured target-phase fraction `p`, the optimistic perfect-removal lower bound is `T*(1-p)`; a phase speedup of `s` predicts `T*((1-p)+p/s)`. Use this to reject changes incapable of closing the gap. Example, explicitly hypothetical: a 60-second year with 30% of time in a target function cannot reach 30 seconds solely by optimizing that function, even infinitely. No percentage or final speedup is promised in advance.

Once the primary target is met across the matrix, stop optional optimization and finish feature/regression work. If only the backup is reached, retain that achieved status and quantify the remaining gap. If both are missed, ship no false success: publish the best verified result, bottleneck table, and next bounded candidate. The overall development time is not provably bounded until native hook compatibility and baseline costs are known.
